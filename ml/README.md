# AccessGuard Quarterly ML Service (V9)

This folder replaces the old, disconnected ML application. It is an **inference-only microservice** for the main AccessGuard backend.

There is deliberately **no frontend, no second review dashboard, and no separate business database** inside this folder. The root AccessGuard project remains the system of record for employees, accounts, entitlements, logs, policies, review cycles and human decisions.

## What this service does

- Loads three independently trained Isolation Forest pipelines: Windows AD, Linux and GitHub.
- Scores **one row per technical account per 90-day review window**.
- Returns an advisory anomaly percentile (0.0–1.0 and 0–100) to the root backend.
- Refuses cross-platform fallback. GitLab and unknown sources remain unscored.
- Refuses ML scoring when the window is not 90 days or when usage-log coverage is unknown / below 99.5% of the window.
- Verifies the model artifact SHA-256 against its JSON manifest before loading it.
- Does not fit a model during an API request, does not revoke or certify access, and does not decide whether access is authorized.

## Architecture boundary

```text
Windows / Linux / GitHub connectors
                |
                v
       Root AccessGuard backend
       - identity/account resolution
       - event normalization + deduplication
       - 90-day feature aggregation
       - policy + mandatory review rules
       - reviewer task + decision history
                |
                | POST /v1/score/accounts
                v
       ml/ service (port 8001)
       - load trusted platform artifacts
       - validate feature contract
       - score each supported platform separately
       - return advisory percentile only
                |
                v
       Root backend combines ML advisory output with policy rules
       and saves the quarterly human review queue.
```

## Important cold-start rule

Do not treat synthetic training rows as a company's normal-behaviour baseline. For a new company with no verified historical baseline:

1. Configure employees, account mappings, entitlements, approved-resource policy, AD group catalog and log sources.
2. Collect a complete 90-day evidence window. Missing logs are an evidence gap, not zero usage.
3. Run an initial human review/pilot. The reviewers' verified outcomes become the reviewed baseline/evaluation data.
4. Train on reviewed baseline-normal records only (`label=0`). Keep confirmed concerns (`label=1`) for independent evaluation and later controlled feedback; do not silently turn unknown cases into normal labels.
5. Freeze the trained model and validate it in a second blind review period before operational prioritization.

The supplied synthetic dataset is suitable for a reproducible development smoke test, not for declaring an enterprise production model validated.

## Train from the supplied account-cycle dataset

Run from `AccessGuard/ml/backend` in a Python 3.11/3.12 virtual environment:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
$env:AEGIS_PLATFORM_MODEL_DIR = (Resolve-Path .\ml_artifacts\platforms).Path
python -m app.ml.platform_train --csv "C:\path\to\AccessGuard_ML_Datasets\data\training_account_cycles.csv" --trees 160 --seed 42
```

Linux/macOS:

```bash
python -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
export AEGIS_PLATFORM_MODEL_DIR="$(pwd)/ml_artifacts/platforms"
python -m app.ml.platform_train --csv /path/to/AccessGuard_ML_Datasets/data/training_account_cycles.csv --trees 160 --seed 42
```

This dataset has 30,000 account-cycle rows (10,000 per platform), `group_id` and `label`; the model code uses a group-based holdout and fits the Isolation Forest on `label=0` training-partition rows only. Its labels are synthetic (`0` throughout), so it cannot produce meaningful positive-class recall/precision during training. Do not describe the resulting files as enterprise-trained or enterprise-validated.

The three artifacts/manifests are written to:

```text
backend/ml_artifacts/platforms/
  windows.joblib
  windows.json
  linux.joblib
  linux.json
  github.joblib
  github.json
```

Artifacts are intentionally not committed in this package. Supply them through a controlled artifact directory/volume after training. Joblib artifacts are executable pickle-based files: load only artifacts generated by this trusted training code and stored in access-controlled locations.

## Evaluate with the separate 90-day test ground truth

The test feature table does not contain the labels. Join its labels only after inference with `test_90day_ground_truth.csv`:

```bash
python -m app.ml.platform_evaluate_90day \
  --features /path/to/AccessGuard_ML_Datasets/data/test_90day_account_cycles.csv \
  --ground-truth /path/to/AccessGuard_ML_Datasets/data/test_90day_ground_truth.csv \
  --out ./evaluation_90day_synthetic.json
```

The evaluator filters `ml_eval_eligible=1`, respects the coverage gate, and reports ROC-AUC, average precision and recall/precision at 5/10/20% review budgets where both label classes are available. The report is explicitly marked synthetic-only.

## Start the service

Set a random `ML_SERVICE_TOKEN` of at least 32 characters. Use the same secret in the root backend. The service does not have a browser-facing CORS policy because the React frontend must call the root AccessGuard API, not this service directly.

Local:

```powershell
$env:ML_SERVICE_TOKEN = "<same-random-secret-as-root-backend>"
$env:AEGIS_PLATFORM_MODEL_DIR = (Resolve-Path .\ml_artifacts\platforms).Path
python -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

Health and model status:

- `GET http://127.0.0.1:8001/health` — process liveness.
- `GET http://127.0.0.1:8001/v1/models` — loaded / missing / invalid model status.
- `GET http://127.0.0.1:8001/v1/ready` — ready only when all three models are loaded and verified.

Restart the service after replacing/training artifacts; the registry is loaded at process startup. There is no hidden auto-training or batch-fit fallback.

## Inference API

`POST /v1/score/accounts` requires `Authorization: Bearer <ML_SERVICE_TOKEN>`.

Request example (feature values are illustrative only):

```json
{
  "cycle_id": "2026-Q4",
  "window_days": 90,
  "records": [
    {
      "account_id": "internal-account-123",
      "platform": "Windows AD",
      "features": {
        "department": "IT",
        "account_type": "human",
        "permission_profile": "standard",
        "entitlement_count": 5,
        "privileged_entitlements": 0,
        "sensitive_entitlements": 0,
        "successful_logins_window": 28,
        "failed_logins_window": 1,
        "resource_use_events_window": 22,
        "active_days_window": 35,
        "distinct_resources_used_window": 4,
        "permission_changes_window": 0,
        "use_age_days": 2,
        "use_evidence_observed": 1,
        "resource_uses_month_1": 8,
        "resource_uses_month_2": 7,
        "resource_uses_month_3": 7,
        "log_coverage_days": 90,
        "log_coverage_known": 1,
        "ad_group_count": 3,
        "privileged_ad_group_count": 0,
        "ad_group_data_known": 1,
        "group_changes_window": 0,
        "transfers_window": 0,
        "recent_transfer_flag": 0,
        "out_of_scope_ad_group_count": 0,
        "mapped_access_ad_group_count": 3,
        "unmapped_ad_group_count": 0,
        "group_catalog_coverage_fraction": 1.0,
        "manager_changes_window": 0,
        "department_changes_window": 0,
        "ad_department_mismatch": 0,
        "windows_privileged_logon_events": 0,
        "windows_privileged_logon_coverage_known": 1
      }
    }
  ]
}
```

Response values:

- `status=scored`: a trained model scored the account.
- `status=unscored`: the response includes a specific reason such as `model_not_trained`, `unsupported_platform`, `model_window_mismatch`, `insufficient_or_unattested_90_day_log_coverage` or `invalid_features`.
- `anomaly_percentile_0_1`: 0–1 percentile relative to the model's verified-normal reference population.
- `anomaly_percentile_100`: same value expressed as 0–100 for display.

A high percentile means unusual relative to the model reference population; it is not the probability of malicious activity or proof of unauthorized access.

## Required root integration

Use `ANTIGRAVITY_INTEGRATION_PROMPT.md` (provided beside the `ml/` folder) as the implementation hand-off. It explains how to:

- replace the old `backend/mock_ml_service.py` runtime path;
- make `backend/ml_client.py` call this `/v1/score/accounts` contract;
- aggregate actual root database data into these account-level feature rows;
- extend the root data schema with explicit log coverage, AD group catalogue/history, HR transfers and managed-resource policy where those sources exist;
- quarantine unknown/ambiguous log identities instead of linking them to the first account;
- add quarterly account review-cycle APIs and connect them to the existing root frontend;
- ensure every transfer/lifecycle trigger bypasses the review budget and every final decision remains human-controlled.

Until that root integration is complete, replacing this folder alone does not magically connect the models to the existing dashboard.
